## Как вставлять

1. Копируй блок текста в нужный раздел ниже (или добавь новый подраздел).

```markdown
**Слабое место / блокер:** (если есть)

(твой текст)
```

## 🎙️ Voice Layer

## Voice Layer — как это работает

Это сквозная шина команд. Любой модуль системы управляется голосом, не только лиды.

**Цикл команды:**

```
Ты говоришь
    ↓
Whisper (Groq) — аудио → текст
    ↓
Hermes — парсит текст → JSON {module, intent, params}
    ↓
LangGraph — роутит к нужному агенту / инструменту
    ↓
Действие (CRUD, поиск, email, аналитика...)
    ↓
UI-реакция
```

**Четыре типа UI-реакций:**

| Реакция | Когда | Пример |
|---------|-------|--------|
| Модалка | Агент вернул текст | Письмо, анализ, ответ → оверлей с кнопками «Отправить / Сохранить / Отклонить» |
| Навигация | Команда про объект | «Открой Нерудную» → `/leads/123` |
| Фильтр | Команда про список | «Просроченные задачи» → фильтр применяется автоматически |
| Апрув | Деструктив или отправка | «Отправляй» → подтверждение голосом или кнопкой |

**Что сейчас работает (Фаза 1):**
Голос → лиды. Hermes умеет только интенты по лидам — CRUD, смена стадии, задачи.

**Что нужно сделать (Фаза 2):**
- Hermes расширяется: модуль + интент для email, поиска, аналитики, базы знаний
- UI получает событие `voice_action` и умеет рендерить модалку с ответом агента
- Навигация через роутер SvelteKit по голосу

**Фаза 3:**
- Голосовое подтверждение («да, отправляй» / «нет, отмени») — сейчас только кнопка
- История команд в Ops → Voice

**Самое слабое место сейчас** — Hermes знает только лиды. Как только хочешь голосом работать с email или аналитикой, он не поймёт. Это первое что нужно расширять в Фазе 2.

## 📧 Email-агент

## Email-агент — что планируется

**Статус:** модуль существует в UI (`/email`), полная функциональность — Фаза 2–3.

---

**Как будет работать цикл:**

```
Входящее письмо (IMAP)
    ↓
Агент определяет тип
(вопрос / апрув / жалоба / спам)
    ↓
Маркетолог готовит черновик ответа
    ↓
Модалка в UI → ты читаешь
    ↓
Голос: «отправляй» / «нет, переделай»
    ↓
SMTP отправляет
```

---

**Все функции по фазам:**

| Функция | Фаза | Описание |
|---------|------|----------|
| Подключение ящика | 2 | IMAP/SMTP, OAuth или app password |
| Список входящих | 2 | `/email`, фоновый синк |
| Анализ типа письма | 2 | агент определяет что это |
| Черновик ответа | 2 | Маркетолог пишет, ты апрувишь |
| Отправка по команде | 2 | голос «отправляй» или кнопка |
| Рассылки | 3 | сегмент лидов → текст → отправить |
| Автоответ FAQ | 3 | простые вопросы агент закрывает сам |
| Цепочки 20 касаний | 3 | Маркетолог ведёт автономно |
| Автолинк → лид | 3 | домен письма → карточка лида |

---

**Голосовые команды которые будут работать:**

```
«Подготовь ответ на письмо от Hochland»
«Отправляй»
«Нет, переделай — сделай короче»
«Составь рассылку по квалифицированным лидам»
«Что пришло сегодня важного»
«Есть ли письма требующие срочного ответа»
```

---

**Архитектура подключения:**

```
credentials в .env (никогда не в коде)
    ↓
IMAP worker — фоновый синк каждые N минут
    ↓
PostgreSQL — хранение писем и статусов
    ↓
Агент-маркетолог — основной исполнитель
    ↓
SMTP — исходящие
```

---

**Автолинк письмо → лид (Фаза 3):**
Если письмо пришло с домена `hochland.ru` — система автоматически находит лид Hochland и прикрепляет письмо к карточке. История коммуникаций в одном месте.

---

**Главный принцип — апрув перед отправкой:**
Агент никогда не отправляет сам без твоей команды. Всегда модалка → ты решаешь. Автоответ FAQ — единственное исключение, настраивается в Ops.

## 🔍 Поиск и RAG

## Поиск и RAG — как работает

**Статус:** поиск работает, RAG есть (1592 чанка). Авто-пополнение из поиска — Фаза 2.

---

**Три поисковика — зачем каждый:**

| Поисковик | Сильная сторона |
|-----------|-----------------|
| Serper (Google) | Общий поиск, новости, компании |
| Brave Search | Приватный, без SEO-мусора |
| Tavily AI | Структурированный результат, хорош для агентов |

Все три работают параллельно — результаты агрегируются.

---

**6 режимов поиска:**

```
По компании     — всё о конкретной фирме
Свободный       — любой запрос
Проспектинг     — найти похожих клиентов
Обогащение лида — email, телефон, сайт, ЛПР
Поиск для RAG   — найти и сразу сохранить в базу
Задача агенту   — агент сам решает как искать
```

---

**Цикл поиск → RAG:**

```
Поисковый запрос
    ↓
Brave / Tavily / Serper
    ↓
Результаты
    ↓
Сейчас: показывает в UI
    ↓                        ← Фаза 2
Авто-чанки Q/A → Chroma
    ↓
RAG конкретного агента
    ↓
Агент умнеет от каждого запроса
```

---

**Обогащение лида — самая важная функция:**

```
Голос: «Найди контакты директора Нерудной компании»
    ↓
Поиск: сайт, LinkedIn, 2GIS, открытые источники
    ↓
Агент извлекает: email, телефон, имя ЛПР, должность
    ↓
Автоматически обновляет карточку лида
```

Это критично — вручную искать контакты тратит кучу времени.

---

**Как RAG устроен сейчас:**

```
Chroma (векторная БД)
    ↓
1592 чанка
    ↓
Разделение по агентам:
├── all       — общая база (все видят)
├── analyst   — данные, метрики
├── economist — финансы, книги (960 чанков)
├── marketer  — B2B-маркетинг (9 материалов)
└── tec       — продукт, документация
```

---

**Что попадает в RAG сейчас vs планируется:**

| Источник | Сейчас | Фаза 2 | Фаза 3 |
|----------|--------|--------|--------|
| PDF вручную | ✅ | ✅ | ✅ |
| Текст вручную | ✅ | ✅ | ✅ |
| Поиск → кнопка «сохранить» | ✅ базово | ✅ авто | ✅ |
| Диалог агента → факты | ❌ | ✅ | ✅ |
| Сайт вендора (краулинг) | ❌ | ❌ | ✅ |
| A/B качества чанков | ❌ | ❌ | ✅ |

---

**Голосовые команды поиска:**

```
«Найди всё о компании Hochland»
«Обогати лид — найди email и телефон»
«Найди в базе знаний про интеграции ManageEngine»
«Сохрани результаты поиска в базу для маркетолога»
«Найди похожие компании на нашего лучшего клиента»
```

## 📋 Лиды / балльная воронка

## Лиды — самый готовый модуль

**Статус:** основная функциональность закрыта кодом. Это база всей системы.

---

**Что есть в UI (`/leads`):**

| Раздел | Что делает |
|--------|------------|
| Воронка | Kanban по стадиям, drag & drop |
| Список | Таблица с фильтрами, сортировка по баллу/приоритету |
| Карточка лида | Все поля, баллы, апрувы, касания, комментарии, история |
| Задачи | Привязаны к лиду, SLA, эскалация |
| Календарь | Следующие звонки и дедлайны |
| Аналитика | Воронка, конверсия, средний чек, цикл сделки |
| Фокус | Pomodoro-режим работы с лидами |

---

**Балльная система — как работает:**

```
Менеджер ставит score (0–100) вручную
    ↓
Система считает suggestedScore по формуле
(стадия + суммы ₽ + задачи + апрувы + просрочки)
    ↓
Показывает подсказку и предупреждения
    ↓
Менеджер решает — менять балл или нет
Агенты score НЕ перезаписывают (agents_may_update_score=false)
```

**Приоритеты по баллу:**

| Балл | Приоритет |
|------|-----------|
| 75–100 | 🔴 critical |
| 50–74 | 🟠 high |
| 25–49 | 🟡 medium |
| 0–24 | ⚪ low |

---

**Что закрыто кодом (P1+P2+P3):**
- CRUD лидов, все поля уровня Битрикс
- `scoreAdvisory` — подсказка без перезаписи
- Суммы в ₽ (`amountRub`, `paidAmountRub`)
- Комментарии к лиду
- Аудит изменений полей
- Правила переходов стадий
- Апрувы и документы (чеклист)
- Лог касаний (звонок/встреча/письмо)

---

**Что агенты могут делать по лиду голосом:**

```
«Пересчитай скор у Нерудной»
«Создай задачу позвонить завтра в 10»
«Покажи историю изменений по этому лиду»
«Маркетолог, напиши письмо для этого лида»
«Аналитик, почему у него низкий балл»
«Переведи лид в стадию Переговоры»
```

— сейчас голос работает базово, полный набор интентов по лидам — Фаза 2.

---

**Связи с другими модулями:**

```
Лид ← Email (автолинк по домену)       Фаза 3
Лид ← Поиск (обогащение данных)        ✅ сейчас
```

## Аналитик — что делает

**Роль:** данные, метрики, отчёты, поиск паттернов в воронке.

**Конкретные задачи:**

| Задача | Пример команды |
|--------|----------------|
| Отчёт по воронке | «Аналитик, сколько лидов в переговорах за май» |
| Скор лида | «Проанализируй Нерудную, почему низкий балл» |
| Поиск похожих | «Найди лиды похожие на наш лучший кейс» |
| Прогноз | «Какова вероятность закрытия этой сделки» |
| Срез по источнику | «Сравни конверсию ManageEngine vs остальные» |

**В оркестрации:**
Стратег часто запускает Аналитика первым — он собирает данные, остальные агенты работают на его выводах. Например:
```
«Проанализируй лид и напиши письмо»
→ Аналитик (данные о компании) ∥ Маркетолог (черновик письма)
→ Стратег синтезирует → модалка
```

**RAG аналитика:**
Пополняется из поисковых запросов по лидам — факты о компаниях, отрасли, рынке автоматически оседают в его базе знаний.

**Что сейчас реально работает:**
Базовая аналитика в `/leads/analytics` — воронка, конверсия, средний чек, цикл сделки. Голосовые запросы к метрикам — Фаза 2.

## Экономист — что делает

**Роль:** всё что связано с деньгами и цифрами по сделке.

**Конкретные задачи:**

| Задача | Пример команды |
|--------|----------------|
| НМЦ по тендеру | «Экономист, какая нормальная цена для этого тендера» |
| Маржа | «Посчитай маржу если дадим скидку 15%» |
| Прогноз закрытия | «Какова вероятность что эта сделка закроется в этом квартале» |
| Финансовый профиль | «Какие финансовые показатели у Нерудной компании» |
| Сравнение сделок | «Какие сделки самые прибыльные по отрасли» |

**В оркестрации:**
Чаще всего работает в паре с Тех. спецом при оценке тендера:
```
«Оцени тендер»
→ Тех. спец (соответствие требованиям) ∥ Экономист (НМЦ, маржа)
→ Стратег: участвовать / нет + обоснование
```

**RAG экономиста:**
Сейчас загружены две книги по экономике (видно в базе знаний — 503 и 457 чанков). Это его основа для финансового анализа.

**Что сейчас реально работает:**
Агент существует, промпт настроен, RAG есть. Голосовые финансовые команды и прогноз закрытия — Фаза 2.


## Стратег — как работает

**Роль:** не выполняет задачи сам — решает кто их выполнит и собирает результат.

**Цикл работы:**

```
Команда (голос или UI)
    ↓
Стратег анализирует задачу
    ↓
Выбирает агентов (1 или несколько параллельно)
    ↓
Fanout — агенты работают одновременно
    ↓
Стратег собирает результаты
    ↓
Синтезирует один финальный ответ → модалка в UI
```

**Сценарии fanout:**

| Команда | Кто работает параллельно | Результат |
|---------|--------------------------|-----------|
| «Проанализируй лид и напиши письмо» | Аналитик ∥ Маркетолог | Анализ + черновик в одной модалке |
| «Оцени тендер» | Тех. спец ∥ Экономист | Участвовать / нет + обоснование |
| «Еженедельный отчёт» | Аналитик ∥ Экономист ∥ Маркетолог | Сводный дашборд |
| «Найди похожих клиентов» | Аналитик ∥ Поиск ∥ Маркетолог | Список + стратегия захода |

**В LangGraph это выглядит так:**

```python
# Стратег — supervisor node
# Остальные — worker nodes
# Fanout: параллельный запуск
# Сбор: все результаты → Стратег → синтез
```

**Что сейчас реально работает:**
Агенты существуют и отвечают по отдельности. Полноценный fanout через LangGraph supervisor — Фаза 2.

**Главная ценность Стратега** — ты говоришь одну команду, он сам решает что делать. Не нужно думать «кому из агентов это поручить».

## Маркетолог — что делает

**Роль:** всё что исходит наружу — письма, рассылки, касания с клиентом.

**Конкретные задачи:**

**В оркестрации:**

**20 касаний — что это:**

**Что сейчас реально работает:**

## Балльная воронка — как работает

**Статус:** полностью закрыта кодом (P1+P2+P3). Работает прямо сейчас.

---

**Главный принцип:**

```
Балл (score) — задаёт менеджер вручную
Подсказка (suggestedScore) — считает система
Агенты — НЕ перезаписывают score (дефолт)
```

Система помогает, не диктует.

---

**Как считается suggestedScore:**

```
Входные данные:
├── Стадия лида (stage)
├── Суммы ₽ (amountRub, paidAmountRub)
├── Задачи (выполнены / просрочены)
├── Апрувы (чеклист документов)
└── Касания (частота контактов)
    ↓
core/lead_score_advisory.py
    ↓
suggestedScore (0–100)
warnings []
breakdown {}
    ↓
НЕ пишет в БД
НЕ меняет score менеджера
```

---

**Что возвращает API:**

```json
{
  "score": 50,
  "scoreAdvisory": {
    "suggestedScore": 45,
    "warnings": [
      "Просрочена задача на 3 дня",
      "Сумма договора не указана"
    ],
    "breakdown": {
      "stage": 20,
      "amount": 0,
      "tasks": -10,
      "approvals": 15,
      "communications": 10
    }
  }
}
```

---

**Приоритеты по баллу менеджера:**

| Балл | Приоритет | Что значит |
|------|-----------|------------|
| 75–100 | 🔴 critical | Работать прямо сейчас |
| 50–74 | 🟠 high | Следующий в очереди |
| 25–49 | 🟡 medium | На этой неделе |
| 0–24 | ⚪ low | Когда будет время |

Пороги настраиваются в Ops → CRM.

---

**Апрувы — чеклист документов:**

```
Влияют на suggestedScore (не на score):
├── КП отправлено
├── НДА подписано
├── ТЗ согласовано
├── Договор на согласовании
└── Счёт выставлен

Каждый апрув добавляет бонус к подсказке.
Веса апрувов настраиваются в Ops.
```

---

**Правила переходов стадий (P2):**

```
Нельзя перейти в «КП отправлено»
без заполненного поля «сумма договора»
    ↓
API вернёт:
{
  "stage_transition_blocked": true,
  "reason": "Заполни amountRub перед отправкой КП"
}
    ↓
UI показывает предупреждение
```

Правила настраиваются в Ops → CRM → JSON.

---

**Аудит полей (P2):**

```
Каждое изменение ключевого поля:
├── Кто изменил (X-Actor-Name)
├── Что было → что стало
├── Когда
└── Источник (менеджер / агент / система)

Доступно в карточке лида → История полей
```

---

**Флаги в crm_settings.json:**

| Флаг | Дефолт | Что делает |
|------|--------|------------|
| `manager_sets_score` | true | Балл задаёт менеджер |
| `agents_may_update_score` | false | Агенты не пишут в score |
| `scoring_advisory_enabled` | true | Подсказка включена |

Меняются в Ops → CRM без правки кода.

---

**Голосовые команды по баллам:**

```
«Пересчитай скор у Нерудной»
→ система показывает suggestedScore + warnings

«Почему у этого лида низкий балл»
→ Аналитик объясняет breakdown

«Покажи все лиды где подсказка
сильно расходится с баллом менеджера»
→ фильтр в списке лидов
```

---

**Веса скоринга — как настроить:**

```
Ops → CRM → scoring_advisory → JSON:

{
  "weights": {
    "stage": {
      "Новый": 10,
      "Квалифицирован": 20,
      "КП отправлено": 35,
      "Переговоры": 50,
      "Выигран": 100
    },
    "amount_rub": {
      "threshold": 1000000,
      "max_bonus": 20
    },
    "tasks": {
      "completed_bonus": 5,
      "overdue_penalty": -10
    },
    "approvals": {
      "per_approval": 5,
      "cap": 25
    }
  }
}
```

Меняешь цифры — формула пересчитывается. Без правки Python.

---

**Главная ценность:**
Не магия LLM а прозрачная формула. Открываешь лид — видишь почему он горячий или холодный. Объяснимо любому.

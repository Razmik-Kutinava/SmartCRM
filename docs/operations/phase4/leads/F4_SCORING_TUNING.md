# Ф4 — Баллы (тюнинг после P3)

**Откуда:** P3 закрыл SLA, экспорт отчёта, `scoreAdvisory` на карточке, приоритет в списке.  
**Зачем Ф4:** закрыть **операционные дыры** — РОП и менеджер должны настраивать и видеть баллы без JSON и без «открыть каждую карточку».

**Не путать с «Мой день»:** ежедневная очередь (`dayRank`, этап+задачи+время) — отдельный блок [`F4_DAY_PRIORITY.md`](F4_DAY_PRIORITY.md). Скоринг даёт `score`/`suggestedScore`; day-priority **не перезаписывает** балл в БД.

База P3: [`F3_SLA_PROTOCOLS_ACCEPTANCE.md`](../../phase3/leads/F3_SLA_PROTOCOLS_ACCEPTANCE.md), [`F3_SCORING_EXPORT_ACCEPTANCE.md`](../../phase3/leads/F3_SCORING_EXPORT_ACCEPTANCE.md).

## Критичные пробелы после P3

| # | Проблема | Почему критично |
|---|----------|-----------------|
| 1 | На карточке: «веса в Ops → scoring_advisory», в `/ops/crm` редактора **нет** | РОП не может менять формулу без правки `crm_settings.json` |
| 2 | `breakdown` считается, в UI **не показан** | PRD: прозрачность подсказки; менеджер не понимает «почему 43» |
| 3 | Список лидов: только `score` менеджера, без флагов advisory | Нельзя отфильтровать «расхождение» / «есть warnings» в ежедневной работе |
| 4 | Прогноз закрытия только на `/leads/analytics` | Балл и шанс сделки разорваны; оператор живёт в карточке |
| 5 | Пороги CRM (85/70/40) ≠ лидоген (80/60/40) | Один лид — разный приоритет в охоте и в CRM |
| 6 | Расхождение балла не в Ops (в отличие от SLA-эскалации) | РОП не видит сводку «кривых» лидов без ручного экспорта |

## План Ф4 (чеклист)

### A. Настройки весов в Ops (блокер)

- [x] Секция в `/ops/crm`: `scoring_advisory_enabled`, JSON или форма для `scoring_advisory`
- [x] Поля: `suggested_score_by_stage`, `approval_weights`, штрафы просрочки, `manager_score_divergence_warn_ratio`
- [x] Сохранение через существующий `PUT /api/ops/crm-settings` (без нового API, если хватает схемы)
- [x] Убрать ложную ссылку «веса в Ops» с карточки, пока UI не готов — или закрыть пункт этим шагом

### B. Прозрачность на карточке лида

- [x] Раскрываемый блок **breakdown** подсказки: этап, сумма, апрувы, штраф за задачи
- [x] Сохранить правило: **балл менеджера не перезаписывается**

### C. Список лидов — риск по баллу

- [x] Лёгкие поля в `GET /api/leads` (без полного advisory на каждый лид): `hasScoreWarnings`, `scoreDivergent` (или аналог)
- [x] Фильтры в `/leads/list`: «с предупреждениями», «расхождение с подсказкой»
- [x] Сортировка опционально: по числу warnings / по delta score

### D. Связка с аналитикой (перекрёст с Analytics v2)

- [ ] Прогноз на **карточке** лида: %, ожидаемые ₽, tier — те же `score` + стадия
- [ ] Детали и калибровка: [`F4_ANALYTICS_V2_TUNING.md`](../analytics/F4_ANALYTICS_V2_TUNING.md)

### E. Единые пороги CRM ↔ лидоген

- [ ] Один источник `priority_thresholds` из `crm_settings` **или** явная подпись в UI лидогена «отдельная шкала»
- [ ] Документировать в `leadgen` README, если оставляем раздельно

### F. Видимость для РОП

- [ ] Минимум: badge/счётчик на Ops или фильтр «только divergent» рядом с экспортом баллов
- [ ] Опционально: запись в Ops queue при сильном расхождении (без Telegram — по аналогии SLA)

## Не в Ф4 (явно вне scope)

| Тема | Почему |
|------|--------|
| Авто-запись `score` формулой в БД | P1: балл задаёт менеджер |
| Автоскор в шапке (GET API) | ✅ Ф4 сделано 2026-11-14: `score = score_manual или scoreAdvisory.suggestedScore` в ответе API; `score_manual` — ручное переопределение; в БД `score` не перезаписывается |
| LLM для скоринга | Вне детерминированной модели |
| Ещё один формат экспорта | P3 закрыт (`scoring/export`, smoke) |
| `RecalculateAllLeadsJob` | `scoreAdvisory` считается на лету при GET карточки |

## Критерии готовности (acceptance)

- [ ] РОП меняет вес стадии «Новый» в UI → на карточке меняется `suggestedScore` без правки файлов
- [ ] Менеджер видит breakdown «28 + 15 − 8» на карточке
- [ ] В списке фильтр «расхождение» показывает только нужные лиды
- [ ] На карточке виден прогноз закрытия рядом с баллом
- [ ] Нет противоречия приоритета CRM vs лидоген без объяснения в UI

## 1. Зачем

Оператору нужен **единый «мой день»** для всех ответственных в SmartCRM:

- Не хронология B24 «как завели задачи», а **умная очередь**: что делать сегодня, что горячее, что можно отложить.
- **Одинаковые правила** при смене фильтра менеджера (кросс-селл: «что у коллеги в приоритете»).
- Верх дня **коррелирует** с баллом и этапом воронки, если карточка заполнена.

---

## 2. Главный принцип (исправление ранней спеки)

| Приоритет сигнала | Источник | Роль |
|-------------------|----------|------|
| **1 — близость к деньгам** | `stage` + `approvals` + `dealPath` | Менеджер ведёт клиента по roadmap; **этап и галочки** — источник правды «где сделка» |
| **2 — что делать сегодня** | Тип открытой задачи | «Ответ на КП» vs «письмо вендору» — разный вес **при одном этапе** |
| **3 — время** | `due` задачи | Просрочка → сегодня (с часом) → без времени → завтра и дальше |
| **4 — затухание** | Повтор «жду ответ» без движения | Высокий этап + месяцы ожидания → **не вечно №1** |

**Не опираться только на ключевые слова в title задачи из B24** — у разных менеджеров разные формулировки. Текст дела — **вторичный** сигнал (regex/словарь) или **тип из dropdown** при создании задачи в CRM.

## 4. Слои ранжирования `dayRank`

### Слой A — время (база)

1. Просроченные открытые дела  
2. Дела **сегодня** — раньше по **времени** в `due` (08:00 выше 08:30)  
3. Дела без времени — ниже тех, у кого время есть  
4. Завтра и дальше — **ниже всего «сегодня»**

### Слой B — близость к деньгам (этап + roadmap)

Вес из:

- **Этап воронки:** Новый → Квалифицирован → КП отправлено → Переговоры → Выигран (Проигран — вниз)
- **Прогресс `dealPath`:** какие галочки закрыты (ЛПР, КП отправлено, счёт, договор…)
- **`suggestedScore` / `score`** — tie-break и корреляция с топом дня
- **`deal_amount`** — tie-break при равном ранге

Подсказки `lead_stage_hints` **напоминают** менеджеру обновить этап и галочки — не заменяют `dayRank`, а показываются рядом.

### Слой C — тип задачи (вторичный)

На **лучшее открытое дело** лида (`nextTask` из flags) + опционально `taskIntent` из CRM:

| Tier | Примеры intent | Смысл |
|------|----------------|-------|
| **A** | `kp_followup`, `kp_send`, `renewal`, `procurement_status` | Близко к оплате |
| **B** | `call`, `meeting`, `email_reply`, `vendor_letter`, `reactivation` | Активная работа |
| **C** | `trial_request`, `testing` | Срочно, но не «ждём деньги» |
| **D** | `find_contacts`, `mailing`, `application_review`, `version_reminder` | Низкий приоритет дня |

**Один и тот же intent + разный этап** → разный итоговый ранг (пример: «письмо вендору» на «КП отправлено» — средний; «ответ на КП» на том же этапе — выше).

Классификация v1: regex/словарь в конфиге (`crm_settings` или `data/lead_task_intents.json`). Не ML.

### Слой D — затухание «зависшего ожидания»

**Проблема:** этап «КП отправлено», задача «жду ответ» повторяется неделями — лид **не должен** вечно быть вверху только из‑за высокого этапа.

**Сигналы stale:**
- Однотипные задачи «ожидание ответа» без смены этапа / без касания (`last_comm_at`)
- `days_on_stage` выше лимита (`lead_stage_hints` уже знает лимиты)
- Повтор intent `kp_followup` / `wait_client` N раз подряд

**Действие:** понижение `dayRank` (decay), суфлеры: «3 недели без ответа — перенести срок / закрыть / проигран?» — расширение `lead_stage_hints`, коды `wait_stale`, `repeat_wait_task`.

### Слой E — полнота карточки (`needsEnrich`)

- Горячий этап/intent (Tier A/B) + `!card_ready` → бейдж **«дозаполни паспорт»**
- **`dayRank` не опускать сильно** — срочность видна, но менеджер знает про дырки

Флаги: `lead_coverage` (`bitrix_full`, `passport`, `card_ready`).

## 6. Типизация задач (шаг 2, после базового ранга)

При создании задачи в CRM — **выпадающий список** типов (не обязателен в v1):

- Перезвонить, Отправить КП, Ответ на КП, Написать письмо, Письмо вендору, Тех. вопрос в поддержку, Встреча/ВКС, Продление, Жду ответ клиента, Найти контакты, …

Поле: `task_intent` (enum) в `tasks` или `note` маркер `intent:kp_followup`.

Импорт из B24: fallback `classify_task_intent(title)` по словарю.

---

## 7. Формула (для имплементации)

Меньше `dayRank` = выше в списке.

```
dayRank(lead) =
  urgencyBucket(overdue=0, today=1, tomorrow=2, later=3)     # слой A
  + timeKey(due_datetime)                                     # внутри дня
  - stageBoost(stage, dealPath_progress)                      # слой B — главный
  - taskIntentWeight(intent, stage)                           # слой C
  - scoreBoost(normalized score or suggestedScore)
  + waitStalePenalty(repeat_wait, days_without_touch)         # слой D

needsEnrich = (intent tier A|B OR stage >= «КП отправлено») AND NOT card_ready
```

При равенстве: `deal_amount DESC`, `company ASC`.

Конфиг весов: секция `day_priority` в `crm_settings.json` (редактирование в Ops — шаг позже).

## 8. Связь со скорингом

| Поле | Роль в «мой день» |
|------|-------------------|
| `score` (менеджер) | Источник правды для фильтров; участвует в tie-break |
| `scoreAdvisory.suggestedScore` | Подсказка; близость к этапу уже в `suggested_score_by_stage` |
| `approvals` | Прямой сигнал «близость к деньгам» |
| Штраф просрочки в advisory | Дублирует слой A — не суммировать дважды |

**Не авто-записывать `score` из `dayRank`.**

## 11. Критерии приёмки

1. Один набор лидов Размика/Константина при смене менеджера — **та же логика** ранжирования.  
2. Этап «КП отправлено» + задача «ответ на КП» 08:00 **выше** «триалка» 08:30 в тот же день.  
3. Завтрашние дела **ниже** всех сегодняшних.  
4. Горячий этап + пустой паспорт — **в топе** + бейдж `needsEnrich`.  
5. Лид «жду ответ 3+ недели» без касаний — **ниже** свежих горячих; суфлер `wait_stale`.  
6. Не ломать фильтры `taskDueToday` / `taskOverdue` из `lead_task_list_flags`.  
7. Unit + integration тесты зелёные; регрессия `crm_leads`.

### Пример целевого порядка (один день 24.06)

1. 08:00 «ответ на кп» — этап КП/переговоры  
2. 08:00 «продление» — этап «На подписке»  
3. 08:30 письма / прайс (Tier B)  
4. 08:30 «получить триалку» (Tier C) — **ниже** КП при том же времени  
5. «найти контакты» / «рассылка» — низ дня
